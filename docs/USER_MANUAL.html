This manual is interactive. Hover any heading and click
    ✎ make a note to file an idea, feedback, or a
    bug against that section. A ▶ icon marks a feature with roadmapped
    changes; click it to preview the planned state. Terms with a dotted
    underline show a short definition on hover, once, before the manual
    explains them in full. Every entry in the contents panel has a handle
    in its left margin, which appears when your cursor moves into the
    margin beside it; drag the handle to rearrange the manual, and your
    browser keeps that order for every visit. Click into any line of
    prose to correct it, and press Enter to keep the change. On a screen
    too small to hold the contents, a menu button in the upper left
    carries them instead.

    
Notes copy as a payload for a
    Claude Code session, which writes the developer ticket. Nothing leaves
    this file until you paste.

  


  

    
Get the plugin.

    
living-manual runs inside Claude Code. Add the repo as a marketplace
    and install:

    
/plugin marketplace add dougstanford/living-manual
/plugin install living-manual@living-manual

    
Or clone the repo and point a session at the checkout:

    
git clone https://github.com/dougstanford/living-manual.git
claude --plugin-dir /path/to/living-manual

    
In any repo you want documented, run
    /living-manual:manual and answer the setup questions. You
    get a page like this one: your product, your brand, your code. The rest
    of this manual explains what that page does.

    
Requires git and python3. Tracker sync needs the
    Atlassian MCP (Jira) or the gh CLI (GitHub Issues).

  


  

    
One file that stays true.

    
living-manual is a Claude Code plugin. Point it at a repo
    and it writes a branded, interactive user's manual, then holds that manual
    to the code as releases ship.

    
The manual is one self-contained HTML file. No build step, no server,
    no external assets: it opens in any browser and travels with the repo.
    This copy lives at docs/USER_MANUAL.html and documents the
    plugin itself, built by the plugin.

    
Three parts keep it honest. A base marker records the commit the manual
    last matched. A pre-push guard blocks releases that would leave the manual
    behind. And an update flow reads only what changed since the marker and
    revises only the sections those changes touched.

    
Reading it is also writing it. Headings take notes that become
    developer tickets. Features with planned changes carry roadmap previews,
    so feedback lands on the plan instead of the past. A queue check shows
    what's already filed, so duplicates become additions. The rest of this
    manual walks each of those surfaces.


    
Fix a line as you read it.

    
Wrong words are easiest to fix at the moment you notice them.
    Click into any paragraph, heading, list item, or the title itself,
    and the block you clicked becomes editable with the caret where you
    put it. Press Enter to keep the change and step back out;
    Shift+Enter breaks a line inside the block; Escape abandons the
    block and restores what it said. Dragging across the words still
    selects them, as it should: a click and a drag are told apart by
    whether the pointer moved and whether it left a selection
    behind.

    
The heading affordance moved out of the way to make room. Filing
    a note is now the pill's job rather than the whole heading's, so the
    words of a heading can be corrected without a modal opening over
    them.

    
Edits keep themselves in your browser and survive a refresh, and
    they change nothing in the file. When the wording is worth keeping
    for everyone, Commit copy appears beneath
    the contents. It is there whenever what this browser has saved
    differs from what the file says, and gone when the two agree, so
    editing a passage back to its original wording puts it away.
    Pressing it copies the prompt, says so underneath, and both fade a
    moment later. It hands the revised passages to a Claude Code session
    that applies them with scripts/recopy.py. That script
    replaces each passage by exact match, so it can prove it is changing
    the text you were looking at, and refuses an edit whose original has
    since changed or appears in more than one place. The button's
    presence is the signal that this browser is holding words the file
    does not have yet.

    
Editing is offered in the sidebar layout
    only. Placing a caret is a pointer's task, and a phone is given the
    manual to read.


    
Arrange it your way.

    
The order a manual is written in is one author's best guess at how it
    should be read. The contents panel lets you test a better one. Each
    entry has a handle in its left margin, three short lines that fade in
    as your cursor comes near and stay out of the way the rest of the
    time. They answer to proximity rather than contact, so a handle is
    already showing by the time you reach it instead of hiding under the
    cursor. Proximity stops at the words: a cursor over an entry's text
    is on its way to the link, and nothing lights up.
    Drag the handle and the entry moves with its subsections; the
    contents show where it will land while the page holds still, and the
    manual glides into the new arrangement when you let go. Change your
    mind mid-drag and press Escape: everything slides back.

    
An arrangement keeps itself. Your browser stores the order and
    reapplies it every time you open the manual, so there is nothing to
    save and nothing to paste. Dragging an entry back where it started
    clears the stored order the same way it set one.

    
The committed file never changes from the browser. To make your
    order the one everyone opens, Commit TOC
    appears under the contents whenever your order differs from the
    file's. It copies a payload naming the section order; hand that to a
    Claude Code session and scripts/reorder.py moves whole
    sections and their contents entries in the file, touching nothing
    else.

    
The contents only earn their place when they can be read whole.
    In a frame too short to show every entry, or too narrow for a
    sidebar, they fade out before the window can cut them off and three
    flat lines take their place in the upper left. Tapping them dims the
    page, holds it still where it stands, and floats the contents in the
    middle of the screen, set large enough to aim at with a thumb. Tap an
    entry and the menu closes on the way to that section; tap anywhere
    outside it and the menu closes leaving the page where it was.
    Rearranging stays with the panel, because dragging a small handle is
    work for a pointer rather than a thumb.

    
Exports lose the rearranging altogether, the
    drag and the stored order alike, and they lose the editing with it.
    Both write back to a repository an outside reader does not have.
    What an export keeps is the reading: the contents still move between
    the sidebar and the menu with the window.


    
Handing it out.

    
Everything above is built for the people who maintain the code. To
    give a release to a wider audience, export a static copy:

    
python3 scripts/export.py docs/USER_MANUAL.html

    
That writes a second file, USER_MANUAL_prod.html, with the
    note-filing path removed along with the affordances that advertise it.
    Headings stop offering notes rather than offering them and doing nothing.
    Roadmap previews go too, because they describe work that has not shipped
    and that is rarely what you want to hand outside the team. The glossary
    and every word of prose stay: the glossary generates nothing, and removing
    it would only make the copy harder to read.

    
Editing and rearranging go the same way, and for the same reason.
    Both end at a payload for a Claude Code session working in this repo,
    and an outside reader has neither. The export carries no caret and no
    handle in the contents, so nothing on the page offers a gesture the
    file cannot finish.

    
The layout is not part of that. A static copy still reads on
    whatever it is opened on: the sidebar at full width, the menu button
    when the window is too narrow or too short to hold the contents
    whole. That is how the document is read rather than how it is
    changed, so it travels.

    
The part worth knowing is what was never visible. The queue is not
    drawn from a server; it lives inside the file. A distributed manual that
    kept it would publish your backlog and name your issue tracker to anyone
    who opened the source, whether or not anything on screen showed it. The
    export carries no ticket and no tracker name, and verification fails if
    any survived.

    
In place of the base marker, an export carries a line naming the
    version and commit it was built from. That is provenance for a file that
    will outlive its release, and it is also how verification recognises an
    export and judges it by the right rules. The guard's marker is left out
    on purpose: this copy is not the one being kept current, and a staleness
    answer nobody maintains is worse than none.

    
Exports are build artifacts. They are ignored by
    git and regenerated at release, so there is only ever one document anyone
    has to keep true.

  


  

    
Notes become tickets.

    
Every heading here is a feedback surface. The manual meets you at the
    moment of reaction, then carries that reaction into the development loop
    with its context intact.


    
Making a note.

    
Hover any heading and click ✎ make a note.
    Pick a type: an idea for something new, feedback on how a feature behaves,
    or a bug. Write one line on what should change, and as much detail as you
    have. The placeholder text tells you what a useful report of that type
    contains.

    
Copy for Claude Code builds a
    structured payload: your note plus the section, its anchor, the manual
    version, the commit the manual reflects, and instructions for the model.
    That commit pins the code state, so the ticket gets written against the
    behavior you were looking at, not whatever the repo has drifted to since.
    Paste it into a Claude Code session in this repo and the ticket gets
    written. Nothing is sent anywhere; the manual only copies text to your
    clipboard.


    
The queue check.

    
The note modal lists the tickets already queued for the section you are
    annotating, with the rest of the queue one click deeper. Recognize your
    request in the list, mark it as yours, and the payload files your note as
    an addition: the existing ticket updates in place, its requirements absorb
    the new information, and no twin is created.

    
The queue is not only what's on disk. An issue can exist at the tracker
    with no ticket file behind it: filed straight in the web UI, or written on
    a branch that never merged. The index asks the configured tracker for its
    open issues and folds in any the local files don't reference, marked
    at the tracker, no local ticket yet. Filing against one of those
    tells the session to write the missing ticket file first, then update that
    same issue, so recognizing a duplicate repairs the gap instead of widening
    it.

    
The queue is a snapshot. This file makes no network call when you open
    it, so what you see is whatever was true at the last rebuild. That is why
    the queue carries its own age: beside the queue label, the modal shows
    when it was last checked and against which tracker. A queue whose age is
    visible misleads you less than one that simply looks current.

    
Between rebuilds the tracker moves on, so the guard watches for it. On
    every push, and on every CI run, the drifted issues are named along with
    the command that rebuilds them. This one warns rather than blocking: a
    stale queue leaves everything else working and fixes itself on the next
    rebuild, and proving it needs the tracker, which can be down for reasons
    you did not cause. An unreachable tracker is not drift, so it says
    nothing at all.

    
GitHub Issues is read through the gh CLI. Jira
    answers only to the Atlassian MCP, which a script can't call, so a Jira
    queue is reconciled by the ticket skill during a session rather than at
    index time. Either way an unreachable tracker degrades to the local files
    with a warning, never a failed rebuild.

    

      

        
TICKET-0004
          idea
          needs answers

        
Let the queue filter by ticket type.

        
✓ Filing as an addition to this ticket

      

      
Example: the queue check mid-note, after the reader recognized their request

    


    
After you paste.

    
The session grounds the note first: it reads this manual's section, the
    code behind it, and the project's planning docs, then writes a ticket with
    user stories, functional requirements, and acceptance criteria. A
    completeness gate decides whether the ticket is ready to build or needs
    answers first; a thin note is never padded into false precision.

    
Tickets land in docs/tickets/, and the queue index in this
    file updates so the next reader's queue check sees them.

  


  

    
Roadmap previews.

    
A feature with planned changes is a moving target, and feedback on its
    current shape is often feedback on something already being replaced.
    Previews fix the aim.

    
A 
    icon sits wherever a plan exists. Click it (the one in this sentence
    works) to see the planned state, its status, and the roadmap source it
    comes from.

    
The scope rule follows. A note on a previewed item files against the
    plan, not the current behavior; the note modal says so and scopes the
    payload accordingly. An icon inside a heading locks that whole section to
    its plan. An icon inline in a sentence offers its item as an optional
    target.

    
This repo has no roadmapped work today, so the icon
    above opens a demonstration and doesn't rescope notes on this section.

  


  

    
The concept glossary.

    
Product-novel terms carry a dotted underline and a hover definition the
    first time they appear. You have met several already in this manual.

    
The discipline: one alert per concept, on its first instance only, and
    only when that instance falls before the passage that defines the concept
    in full. Once the manual has explained a term, the reminders stop. A
    document that keeps footnoting what you already read is noise.

    
Each entry records where its definition lives, so when prose moves
    during an update, the alert boundary moves with it.

  


  

    
The ticket skill.

    
/living-manual:ticket turns a pasted note, or a free-form
    report, into a developer ticket in docs/tickets/. One ticket
    per submission, unless it clearly contains independent requests.


    
Grounded before written.

    
Every claim about current behavior must be verifiable in code or docs;
    the skill reads the named section and the code behind it before writing a
    word. Classification is honest: designed-but-frustrating behavior is filed
    as feedback naming the governing decision, not as a bug, and a mislabeled
    submission is reclassified with a line saying so.


    
The completeness gate.

    
A ticket is marked ready only when
    every functional requirement is unambiguous and testable, and the
    acceptance criteria cover all of them. Anything resting on a guess flips
    it to needs answers, with open questions
    that carry their own resolution: each names the requirement it blocks,
    proposes a default, and says what changes if the default is wrong. Answer
    them all and the ticket flips to ready.


    
What a ticket contains.

    
    
      
  • A summary, and the submission verbatim as the origin record.
    • 
      
  • Current behavior (or planned behavior, for plan-revision tickets)
        with file references.
    • 
      
  • User stories; every requirement traces to one.
    • 
      
  • Numbered functional requirements, each testable.
    • 
      
  • Given/When/Then acceptance criteria covering every requirement.
    • 
      
  • Open questions, when the gate demands them.
    • 
    


    
The issue tracker.

    
With a tracker configured, each ticket also becomes an issue in Jira or
    GitHub Issues. The ticket file records the issue reference in its
    issue: field, and additions update that same issue rather
    than creating twins. A tracker failure never blocks the local ticket: the
    file is the record, and the report names the retry path.

    
Setup decides which of your labels each note type files under, and it
    only reuses a label that means what the type means. When nothing in your
    project does, it offers to create one named for the type rather than
    filing under the nearest available thing. If it does propose reusing a
    label under a different name, it tells you what that label already
    means, so the compromise is yours to accept rather than yours to
    discover later. Nothing is created without your say-so.

    
A type can carry several labels, not just one, so the issues filed
    here pick up whatever routing labels your project expects and look like
    the issues your team files by hand.

    
Sync never invents taxonomy. A label or issue type named in the config
    but since deleted at the tracker is reported, not recreated. When a type
    carries several labels and one of them is gone, the issue is still filed
    with the rest and the missing one is named: losing a routing label is no
    reason to lose the issue.

    
This repo files to GitHub Issues at
    dougstanford/living-manual, so the queue you see above is reconciled
    against it.

  


  

    
Setup and updates.


    
First run.

    
Install the plugin (claude --plugin-dir /path/to/living-manual,
    or add the repo as a marketplace) and run
    /living-manual:manual in your repo. Setup walks six steps,
    each landing on disk, so an interrupted run resumes where it stopped:

    
    
      
  1. Orientation: the codebase is inventoried and the full feature
        map is printed in the reply for you to read. You confirm or
        correct what's on screen before a word of the manual is
        written.
    2. 
      
  2. Brand: palette, type, and voice are read from your brand assets.
        Without any, a neutral palette stands in and is noted for a later
        pass.
    3. 
      
  3. Tracker: optional. Setup detects the usable providers (Jira via
        the Atlassian MCP, GitHub Issues via the gh CLI), prints your
        project's existing labels, milestones, and issue types, and
        proposes a mapping built from them. Nothing new is created without
        your confirmation.
    4. 
      
  4. Config: .living-manual.json at the repo root records
        all of it.
    5. 
      
  5. Wiring: the pre-push guard installs, CLAUDE.md gains the update
        instruction, and the tickets directory is created.
    6. 
      
  6. Build: the shell is scaffolded, the prose written, and the result
        verified before it's reported done.
    7. 
    


    
Every run after.

    
/living-manual:manual update diffs reality against the
    manual: it lists the user-facing commits since the base marker, revises
    only the sections those changes touch, appends a dated entry to What's
    new, and re-stamps the marker. A manual already matching the code says so
    and stops.

    
Shipped roadmap items lose their previews; the content moves into the
    section and What's new. New concepts enter the glossary with their
    defining passage recorded.


    
The config file.

    
.living-manual.json holds the product identity, paths,
    brand, and tracker settings. The user_facing_paths list decides
    which commits count against freshness: changes elsewhere (CI, tests,
    internal tooling) never block a push. The full key list is in the
    reference below.

  


  

    
The staleness guard.

    
The manual records the commit it last matched: the base marker,
    stamped in a comment near the top of this file and read by the scripts.
    The manual is stale when user-facing commits postdate that marker.

    
Enforcement is layered. CLAUDE.md instructs every session in the
    repo to run the update flow before any push, so freshness is part of the
    normal workflow. The pre-push hook is the backstop: a push with
    user-facing commits past the marker is blocked, with a message naming the
    fix. On GitHub, a workflow repeats both checks on the server, where
    merges land without passing through any hook.

    

      The escape hatch costs the next reader.
      git push --no-verify bypasses the guard once. The push
      succeeds, and the next dev opens a manual describing an app that no
      longer exists. Fix the manual instead; the update flow only revises
      what changed.
    

    
The marker is a sha frozen in this file, so it can outlive its commit.
    Amending or rebasing after an update run orphans the marker: the commit it
    names stops existing while the manual still points there. An orphaned
    marker counts as stale rather than current, and verification flags it,
    since the usual cause is a history rewrite after stamping.

    
Stamping the marker also records a content hash for each user-facing
    path, and those outlive the commit. So a rewrite no longer costs you the
    answer. If every hash still matches, nothing user-facing moved: the
    manual's content is current and re-stamping the marker is the whole fix.
    If a hash differs, the guard names the paths that changed, which is the
    part a missing commit would otherwise have taken with it.

    
Both cases stop a push, because an orphaned marker leaves every later
    staleness check meaningless until someone re-stamps. They stop it with
    different messages, since re-stamping a marker and rewriting a section
    are not the same amount of work. A manual stamped before this existed
    carries only a sha and behaves exactly as it always did.

    
The guard reads user_facing_paths from
    the config, so documentation-only and tooling-only pushes pass
    untouched.


    
The same check on the server.

    
A hook lives in a clone, so it only ever sees a push. A merge
    performed on GitHub never reaches it: a squash, or an "Update branch"
    click, rewrites history on the server and can land a manual that is
    stale or whose marker no longer resolves. Setup offers a workflow that
    runs the same checks where merges actually happen. It asks only on
    GitHub-hosted repos, and records your answer either way.

    
The workflow is one step, because the plugin publishes itself as an
    action:

    
- uses: actions/checkout@v4
  with:
    fetch-depth: 0
- uses: dougstanford/living-manual@v0.2.6

    
Full history is the one thing to get right. The base commit is
    usually far behind HEAD, and a shallow checkout would report a perfectly
    good marker as broken. The check recognises that case and says so,
    rather than sending you to re-stamp a marker that was fine.

    
A failure names the offending commits and the command that fixes
    them. The scripts need no model, so the server can find the problem;
    writing the manual still happens in a session.

    

      Advisory until you say otherwise. A red check does not stop a
      merge on its own. Adding it to the branch's required checks is a
      repository setting, and the plugin does not write it: supplying the
      signal is the plugin's job, deciding its force is yours.
    

  


  

    
Reference.


    
Config keys.

    

      
KeyMeaning

      
product, tagline, tagline_pill
        Identity shown in the manual's hero.

      
manual_path
        Where the manual lives. Default docs/USER_MANUAL.html.

      
tickets_dir
        The ticket queue. Default docs/tickets.

      
ticket_skill
        The command the note payload invokes.

      
user_facing_paths
        Path prefixes whose commits make the manual stale.

      
brand
        ink, surface, deep, accent, warn, caution, font stack, hero
        gradient, logo data URI. Missing keys fall back to a neutral
        palette.

      
tracker
        Provider (jira, github, or none) and that provider's block:
        project key or repo, plus the note-type mapping onto issue types or
        labels. A type maps to one label or a list of them. A legacy
        jira block still reads.

      
ci
        Whether the server-side check was wired up, and where its
        workflow lives. provider: none with a reason when it
        was declined or unavailable.

    


    
Scripts.

    
The scripts do the mechanical work so model time goes to content and
    judgment. All run from the plugin; nothing needs installing.

    

      
ScriptDoes

      
state.sh
        One JSON line: configured or not, manual base, HEAD, wiring.

      
inventory.sh
        Codebase orientation for setup: framework signals, surfaces,
        docs, brand candidates.

      
stale.sh
        CURRENT, or the commits and user-facing files since
        the base marker. After a history rewrite, compares content hashes
        instead. Exits 0 current, 1 needs work, 2 could not check, 3 needs
        only a re-stamp.

      
ci-check.sh
        Both checks in one command, for the CI workflow: verification
        and staleness, each reported even when the other fails.

      
install-hook.sh
        Installs the pre-push guard.

      
scaffold.py
        Instantiates the manual shell from the brand config, base
        marker and content hashes included.

      
sync-index.py
        Rewrites the manual's data blocks from a JSON payload. Stamping
        the base also records one content hash per user-facing path.

      
tickets-index.py
        Rebuilds the queue index from the ticket files, then folds in
        open tracker issues no ticket file references, so the queue can't
        drift from either, and records when it did so.
        --check compares without writing and exits nonzero on
        drift. --no-tracker skips the query.

      
next-ticket.sh
        The next free ticket number.

      
recopy.py
        Applies prose revised in the browser: replaces each passage
        by exact match, refuses one whose original moved or repeats, and
        writes nothing unless every edit checks out.

      
reorder.py
        Applies a reader's section order to the manual file: moves the
        section blocks and their contents entries, touches nothing else,
        refuses an id set that does not match.

      
export.py
        A static copy for distribution: note filing, queue, and roadmap
        previews removed; glossary and prose kept.

      
verify.py
        Static integrity checks, including that the base marker resolves
        to a commit in the repo and that its content hashes are readable;
        prints OK or findings. Judges a static export by the rules that fit
        it.

    


    
Ticket statuses.

    

      
StatusMeaning

      
ready
        Complete: requirements testable, criteria cover them, no
        guesses.

      
needs answers
        Open questions block completeness; answering them all flips the
        ticket to ready.

      
shipped
        Landed in a release. Dropped from the queue index, kept as the
        record.

      
declined
        Closed without building. Kept as the record.

    


    
Requires git and python3. With node present,
    verification also syntax-checks the manual's script.

Small screens get the contents as a menu. Rather than clipping
      at the edge of a frame that cannot hold them, they fade out and
      leave three flat lines in the upper left; tapping those dims the
      page, freezes it, and floats the entries in the middle of the
      screen at a size worth aiming at. The page itself now reflows to
      the frame it is given, so commands wrap and wide tables scroll
      inside their own edges instead of dragging the text off screen.

    

    

      
v0.3.1 · July 27, 2026

      
The first run now ends the way setup says it does: with a manual
      that verifies. A freshly scaffolded manual carried a queue stamp
      written in a form the verifier would not read, so the last step of
      setup reported a finding in a file the user had not touched. Repos
      that already ran setup never saw it; the first queue rebuild rewrote
      the stamp correctly, which is why this repo's own manual hid the
      fault. New scaffolds now verify as built.

      
Setup's glossary payload works as documented. The instructions
      said summary; the sync script demanded a different key
      and stopped with an error when given the documented one. It now
      accepts both. A malformed defining-context entry also reads as one
      clear finding naming the mistake, where before it dissolved into a
      cascade of nonsense findings, one per character.

      
Also in this release: install by marketplace
      command, above, and the license names its author.

    

    

      
v0.3.0 · July 27, 2026

      
The manual can now be handed out. Everything that makes it useful to
      the people maintaining the code — notes on every heading, the queue, the
      roadmap previews — is either useless or unwanted in a copy given to a
      wider audience. One command now writes a static version with all of it
      removed, and with the affordances removed too, so no heading offers a
      note it cannot file.

      
The queue was the real reason. It was never fetched from a server; it
      travels inside the file. A copy handed out with it intact would publish
      your backlog and name your issue tracker to anyone who viewed the source,
      whether or not anything on screen displayed it. A static copy carries
      neither, and verification refuses one that does.

      
The glossary survives, because it generates nothing and only makes the
      document easier to read. Exports are build artifacts: ignored by git and
      regenerated at release, so there is still only ever one manual anyone has
      to keep true.

    

    

      
v0.2.9 · July 27, 2026

      
Note types now get labels that mean what they say. Setup used to map
      each type onto exactly one label you already had, and when nothing
      fitted it picked the nearest thing anyway. This manual's own repo was
      the example: nothing here meant feedback, so feedback was filed as
      question, which means someone is asking for information.
      Setup now offers to create a label named for the type instead, and if
      it does suggest reusing one under a different name, it tells you what
      that label already means before you agree to it.

      
A type can also carry several labels rather than one, so the issues
      filed from your manual pick up the routing labels your project expects
      and look like the issues your team files by hand. Configs written
      before this keep working untouched.

    

    

      
v0.2.8 · July 27, 2026

      
The queue now tells you how old it is. It was always a snapshot,
      rebuilt only when someone ran the ticket skill or updated the manual,
      and nothing rebuilt it when the tracker itself moved. So a queue could
      show an issue that shipped last week, or miss one filed yesterday,
      while looking perfectly current. The modal now shows when the queue was
      last checked, and against which tracker, beside the queue itself.

      
Drift also announces itself instead of waiting to be noticed. Every
      push and every CI run compares the published queue against the tracker
      and names the issues that no longer match, along with the command that
      rebuilds them. This one warns rather than blocking: a stale queue
      leaves everything else working, and an unreachable tracker is not
      drift, so it passes in silence rather than failing a push over someone
      else's outage.

    

    

      
v0.2.7 · July 27, 2026

      
A history rewrite no longer costs you the manual's bearings.
      Rebasing, amending, or squash-merging after an update run orphans the
      base marker, and until now that left you knowing only that something
      was broken: with the commit gone there was no range to compare, so
      nobody could say what had actually changed. The marker now carries a
      content hash for each user-facing path, and those survive the
      rewrite.

      
The result is a straight answer. Nothing user-facing moved, and the
      guard says so: the content is current, and re-stamping the marker is
      the whole fix. Something did move, and the guard names which paths, so
      you know where to look without the commit. Both still stop a push, but
      they no longer tell you the same thing. A manual stamped before this
      release carries only a sha and behaves exactly as it did.

    

    

      
v0.2.6 · July 26, 2026

      
The staleness guard now runs on the server as well as in your
      clone. Until now a merge performed on GitHub slipped past it
      entirely: a squash or an "Update branch" click rewrites history where
      no hook is watching, and could land a manual that was stale or whose
      base marker pointed at a commit that no longer existed. Setup offers
      a workflow that repeats both checks on pull requests and on the
      default branch. It is a single line in your workflow file, since the
      plugin now publishes itself as a GitHub Action.

      
A shallow checkout used to be indistinguishable from a broken
      marker. It is now recognised and reported as what it is, so nobody
      re-stamps a marker that was never wrong. The check stays advisory
      until you add it to a branch's required checks.

The queue check now sees the tracker, not just the ticket folder.
      An issue open at the tracker with no ticket file behind it appears in
      the queue marked as such, so the modal can no longer tell you nothing
      is filed while the tracker holds two open issues. Filing against one
      writes the missing ticket file and updates that same issue.
